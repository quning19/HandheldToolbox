## R1 · P1：普通 convert 与 Android build 的保留行为不同

证据：[service.py:55](../../../src/retrolibx/application/service.py#L55)、[handheld.py:280](../../../src/retrolibx/application/handheld.py#L280)、[merge.py:44](../../../src/retrolibx/adapters/esde/merge.py#L44)。

普通 convert 直接生成目标列表并交给 planner，没有 build 的旧 XML 按 ROM 路径合并逻辑，也不输出完整 custom_systems。默认冲突策略会跳过旧 XML，覆盖策略则可能丢失旧收藏、统计及用户字段。把两条入口统一描述为“保留已有列表”会误导使用者。

建议：如普通 convert 也用于更新已有 ES-DE，应复用同一个 ES-DE 合并策略，并明确新建/补齐/覆盖模式；不再在新入口复制合并实现。当前使用时先遵守 [PROJECT_GUIDE.md](../../PROJECT_GUIDE.md) 的入口边界。

## R2 · P1：平台 XML 与识别 JSON 有重复定义，缺少统一配置目录入口

证据：[frontend_platforms/__init__.py:12](../../../src/frontend_platforms/__init__.py#L12)、[同文件:63](../../../src/frontend_platforms/__init__.py#L63)、[platforms.json](../../../src/frontend_platforms/platforms.json)、[handheld.py:103](../../../src/retrolibx/application/handheld.py#L103)。主题工程的 `config/project.json` 同时指定源 XML 与独立 JSON。

最终 XML 在主题工程，本工程读取包内 XML 副本；JSON 又保存 name、ROM 目录、theme、platform、扩展名和 commands 等字段。更新原 XML 不会自动更新这两个副本。系统注册和新输出节点部分字段来自 JSON，完整模板来自 XML，不同步时会混用不同版本。JSON 中的来源哈希是记录，当前不构成自动同步保障。HandheldConfig 也不能注入整套平台配置目录，`systems_template` 只覆盖单个系统表文件。

建议：保留用户已测试的四文件 XML 为维护基线；JSON 主要保存 XML 没有的 aliases、base_platform、variant、badge 等补充信息。提供一个可选 `platform_config_dir`，让两工程读取同一基线；独立发布继续携带固定版本副本，发布时同步。无需引入数据库或配置服务。

## R3 · P2：VIB 核心检查绑定 gpsp_rumble 字符串

证据：[handheld.py:194](../../../src/retrolibx/application/handheld.py#L194)。

需要震动的判断依据是源命令包含 `gpsp_rumble`；即使使用者确认其他命名的核心可用，覆盖命令不含同样字符串也会被阻止。该判断不能证明配置保留或丢失了实际震动功能。

建议：把平台的启动要求及确认策略放入共享平台补充配置或启动 profile，依据明确的平台规则检查。沿用用户已验证的命令，避免强迫固定核心文件名；不要自动降级普通核心。是否震动仍由用户实际启动确认。

## R4 · P2：改输出系统名时，配套排序配置没有同步改引用

证据：[handheld.py:260](../../../src/retrolibx/application/handheld.py#L260)、[同文件:307](../../../src/retrolibx/application/handheld.py#L307)。

`system_ids` 可把选中系统改成新输出名，es_systems 的名称与列表目录随之更新，但 `es_systems_sorting.xml` 等配套文件直接保留旧内容。新名不在原排序配置中时，会失去该平台已配置的排序等元数据关联。默认原命名且复用完整现有配置不触发这个问题。

建议：如确实使用输出别名，精确同步所涉及的系统名引用；保留其他全部系统配置。先明确别名用途，不能整文件做字符串替换。

## R5 · P2：排序规则对平台与多 ROM 的表达不完整

证据：[pegasus/adapter.py:259](../../../src/retrolibx/adapters/pegasus/adapter.py#L259)、[esde/adapter.py:50](../../../src/retrolibx/adapters/esde/adapter.py#L50)、[gamelist.py:151](../../../src/retrolibx/adapters/emulationstation/gamelist.py#L151)。

游戏级 sort-by 被保留，但同一游戏多个 ROM 共用排序键，没有版本间次序；collection sort-by 不参与平台排序生成，平台顺序使用完整目标配置。当前实现可以保持已测试目标平台排序，但不等于全部原天马排序逐项转换。

建议：明确“沿用完整目标平台排序”这一默认策略；如需要天马平台顺序或多 ROM 精确顺序，再用小范围排序策略配置实现。不要未经确认直接修改现有已测试的排序表。

## R6 · P2：developer 的版本说明处理是样本启发式规则

证据：[esde/adapter.py:68](../../../src/retrolibx/adapters/esde/adapter.py#L68)。

源是 Pegasus 且 developer 等于游戏名或以游戏名加空格开头时，目标删除 developer；有额外文字时将其加到简介末尾的“版本说明”。这适合当前样本，却可能误处理其他库的真实开发者或既有简介。该规则位于通用 ES-DE 适配器，影响所有 Pegasus 输入。

建议：默认保持 developer 语义；将天马特定“版本说明字段”行为放进来源 profile，可明确启用并指定识别方式。不要按相似文字自动改变所有输入。

## R7 · P2：天马媒体回退路径写在通用 Pegasus 导入代码里

证据：[pegasus/adapter.py:185](../../../src/retrolibx/adapters/pegasus/adapter.py#L185)、[esde/adapter.py:82](../../../src/retrolibx/adapters/esde/adapter.py#L82)。

缺少或失效的媒体引用按 `media/<游戏名>/{boxfront,logo,video}` 搜索，这是当前天马包约定，其他来源不能调整。ES-DE 目前只导出三个媒体角色；模型可容纳更多媒体，不代表当前都导出了，概要也没有逐字段完整报告所有未导出的源信息。

建议：来源 profile 管理回退目录及资源名；显式引用仍优先。按需求增加媒体角色选择及遗漏说明。`covers/marquees/videos` 等 ES-DE 格式规定的目录名继续放在适配器中，不需要变成任意路径配置。
